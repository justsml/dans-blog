So steal the database connection string

One logical dependency deserves one address.

environment · constructor · call site

// init  (keys and URLs come from .env)
new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY })

// every call site
model: "claude-fable-5-1",
max_tokens: 2000,
cache_control: { type: "ephemeral" }

one string

LLM_URL=llm://anthropic/fable-5.1?cache=true&max=2000

// init, anywhere, any language
const model = connect(process.env.LLM_URL)

Left: the same dependency configured three times in three places. Nobody chose this; it accreted.

Click: the right panel collapses it into one string, consumed by one connect call, in any language.

Click: the anatomy. Scheme says this is a model. Host says who serves it: a provider alias like anthropic, a hostname like api.anthropic.com, a gateway, or localhost:11434. Path names the model. Query carries the knobs.

Settle the first syntax question here so it does not derail Q&A: a local model is a host, not a new scheme. postgres:// did not need a laptop:// variant.

llm:// (15 min) | slide 4 | 2.5 minutes

This is the objection everyone raises, and it is the slide that answers it with evidence instead of an analogy. The table is real output from the llm-strings normalizer: max=2000 becomes max_completion_tokens, max_tokens, or maxOutputTokens depending on the host. cache=5m becomes Anthropic cache control with a TTL or a Bedrock cache point. Unknown vendor params pass through; strict mode rejects them.

Click: validation. cache=2h fails inside your process, before the request leaves. Three names for one knob is exactly the mess a standard envelope exists to hide.

The other two objections

Secrets. And “we already have provider/model.”

“Credentials in a URL?”

llm://app:sk-live-…@openai/gpt-5.6-sol

llm://worker@openai/gpt-5.6-sol + key from env or a secret manager

The userinfo slot exists, the way it does in postgres://. Logs, shell history and telemetry say use it sparingly. Standardize the string; keep credential policy separate.

“We already have a shorthand.”

provider/modelmodel@providerprovider:model{ provider, model, apiKey, baseUrl }

Each one stops at the model name. No home for parameters, no credential position, no parser, nothing to validate. llm://provider/model keeps the shorthand you already use and gives it a query string and a spec.

llm:// (15 min) | slide 5 | 2.5 minutes

Left: yes, the syntax allows a key in the userinfo position. No, that does not license pasting keys into dashboards. A production implementation references the credential by an env indirection or a secret manager and keeps the label. Do not make this a fight; nobody disagrees.

Click, right: the honest objection is that provider/model already won as a de facto shorthand. Agreed. It is the host and path of this URI. What it lacks is everything after the slash: parameters, a credential position, a parser, validation. llm:// is provider/model with a query string and a spec, not a replacement for it.

The bigger idea: stop making every library invent this

A human picking a model once can tolerate awkward config. An orchestrator choosing among cloud, local and specialist endpoints at runtime needs a machine-readable model target.

postgres:// Databases are infrastructure.amqp:// Queues are infrastructure.s3:// Object storage is infrastructure.llm:// Models are becoming infrastructure too.

Let's give them connection strings.
One string. Any model. Any provider. Stop configuring models like it's 1999.

Blog post → Internet-Draft (draft-levy-llm-uri-scheme) → llm-strings on npm, zero dependencies, with a playground. Edge cases should be challenged, syntax should evolve, libraries should experiment. Come argue with me.

llm:// (15 min) | slide 6 | 2 minutes

Every SDK ecosystem reinvents serialization. A URI is a lingua franca between shell scripts, SDKs, agents, eval systems, CI, config managers, routers and observability. That matters more than shaving three env vars.

The agentic argument: if models are infrastructure they need infrastructure-grade addressing, so an orchestrator can accept llm:// the way it accepts postgres, redis, s3 and https.
