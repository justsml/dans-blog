The two objections you are already forming

Secrets, and “every provider is different.”

Yes, URIs can carry credentials. No, you should not paste them into logs.

llm://user:secret@provider/model

llm://provider/model?credential=env:OPENAI_API_KEY

Connection-string standardization is useful. Credential policy still matters. The standard should make secure implementations possible, not pretend URLs solve secret management.

Postgres, MySQL, Redis, and Mongo are not identical either.

llm://provider/model?temperature=.7&vendor.some_feature=true

Connection strings standardize the envelope, not every capability. Common parameters normalize. Provider-specific ones stay namespaced or pass through. It is an interchange format, not a claim that all models are the same.

Bonus: databases eventually encoded SSL, timeouts, replicas, and failover. llms://primary,backup/model is the same problem class.

llm:// (10 min) | slide 4 | 2.5 minutes

Left card, deliberately controversial. URI syntax supports credentials. That does not mean applications should casually put secrets in shell history, telemetry, or dashboards. Separate the two ideas. A production implementation can reference a credential by indirection rather than embedding it.

Right card. Every provider has different options. So do databases. The string standardizes the envelope. Common parameters normalize; vendor parameters get a namespace.

Click for the failover aside if time allows. The article proposes llms:// as a plural form for multi-host behavior. Whether that exact syntax survives matters less than establishing the abstraction.

Why this matters more in an agentic world

A developer picking a model once can tolerate awkward configuration. An orchestrator choosing among cloud, local, and specialist endpoints at runtime needs a portable, machine-readable description of a model target.

postgres://  redis://  s3://  https://llm:// One string. Any model. Any provider.

Stop configuring models like it's 1999.
