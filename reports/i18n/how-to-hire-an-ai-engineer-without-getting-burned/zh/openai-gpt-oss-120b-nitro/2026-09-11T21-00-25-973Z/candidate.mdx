演示可以运行。简历看起来很出色。每个人在面试结束时都兴奋不已。

随后有人会问：如果系统把同一笔退款发放两次会怎样？

沉默是个昂贵的答案。

AI 招聘之所以困难，是因为工作中可见的部分往往提前结束。一个能用流畅段落回答的聊天窗口看起来已经完成。它并没有告诉你系统是否遵守权限、是否能在超时后存活，或每张工单的成本是否高于本应帮助的人工。

你不需要在注意力头上争论到底。你需要足够的证据来决定谁能代表你做出这些决策。

<blockquote class="breakout">
  <p>招聘时要看演示背后的判断力。让这种判断在你发出录用之前就可观察到。</p>
</blockquote>

下面是我对将 AI 投入产品的工程师的招聘流程：先写出预期成果，打开一项真实工作，付费让候选人完成一次短期工作会话，然后对你实际看到的内容打分。研究和基础设施岗位需要不同的练习。先从岗位本身开始。

---

## 在挑选简历前先写岗位需求

“我们需要一名 AI 工程师” 的实用价值堪比 “我们需要一个会理财的人”。会计？CFO？还是那个告诉创始人别再买域名的人？

先确定你要招聘的人要负责的具体问题。

| 需要完成的工作 | 需要寻找的证据 |
| --- | --- |
| 研究或模型开发 | 实验、基线、数据选择，以及对未成功之处的诚实说明 |
| AI 应用工程 | 有价值的工作流、集成、评估以及故障处理 |
| AI 基础设施 | 部署、容量、监控、成本控制和负载下的恢复 |
| 评估与质量 | 具代表性的测试用例、可辩护的评分以及回归诊断 |
| AI 产品工程 | 用户研究、工作流设计、采纳情况，以及功能提升工作的证明 |

一个人可以覆盖多行。期望在全部五类上都有同等深度，就会把岗位描述变成带薪资的愿望清单。

在开启面试前先写出前 90 天的成果。例如：

> 确认支持草稿助手是否能在不增加政策错误的前提下缩短处理时间。交付可衡量的试点、人工审查路径，并给出扩展、修改或停止的建议。

这会给候选人提供反驳的空间，这正是目的所在。优秀的候选人会询问处理时间如何衡量、政策归属谁以及是否有人检查过当前人工答案的质量。弱的候选人则会说这听起来很激动人心。

如果你的团队中没有人能够评判这些技术证据，请邀请外部实践者进行评估——并询问他们是否希望事后向你出售实现方案。否则候选人会自行充当技术参考，这会导致利益冲突，影响更好的姿态。

## 让他们打开引擎盖


一位著名的雇主会告诉你某人曾在哪儿工作。一次演示只能说明某个东西曾在笔记本上、在好心情时运行成功过一次。两者都无法说明此人在你的团队上能承担什么责任。

要求他们完整地讲述一个项目：

**“请详细说明你亲自交付的某个成果。你负责了哪些部分，出现了哪些故障，凭什么证据做了哪些改动？”**

随后沿着一次决策的全流程追问。最初的方案是什么？他们测量了哪些指标？拒绝了哪些备选方案，为什么？同事贡献了什么？现在回头再做会有什么不同？

要求提供一个产出物：一次失败运行的脱敏追踪、评估报告、设计文档、测试用例或简短的代码 walkthrough。追踪就是系统在给出答案过程中的全部记录——每一次工具调用、每一次重试、每一次静默吞掉。它区别于仅仅阅读论文，更像是看到实际的工作过程。

拒绝交出前雇主的客户数据的候选人是在通过测试，而不是在失败。
</p>

可以改用重构后的示例，或使用下面共享的练习。**“展示证据”**绝不能演变成**“让我们获取他人的机密”**。

对于早期职业的招聘者，证据规模可以更小，这没有问题。根据岗位职责和监督层级调整期望范围。你评估的是理解和所有权，而不是能否拿到知名公司的徽标。

## 值得在面试中花时间的五个问题

这些是用于调查的提示，而非问答竞赛。如果仅靠记忆答案就能通过，那这些问题毫无意义。

### 1. “你如何判断这个代理是否有所提升？”

倾听候选人用岗位语言描述成功：正确解决的工单、实际发送的草稿、避免的升级。随后询问平均分数可能掩盖的哪些失败，以及他们会将新版本与什么基准进行比较。

好的回答会让测量过程可检验。让他们现场草绘三个测试用例，并说明由谁决定每个用例是否通过。如果模型对答案进行打分，进一步追问他们如何验证评分器。**“得分 94%”并不是度量，如果同一次运行在周二得分 82%。**[/auto-tune-your-llm-judge]

Anthropic 的[代理评估指南](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)阐明了面试中应关注的区别：代理的行为记录并不等同于最终结果。代理报告“我已发起退款”只是一个句子，而不是退款本身。

### 2. “工具在提交退款后超时。接下来怎么办？”

“重试”是错误的第一反应。钱可能已经被扣除。

倾听他们在采取行动前检查交易状态的做法，是否使用幂等键让第二次请求落在第一次上，以及在状态真正未知时的升级路径。询问谁会看到该失败以及后续工作如何恢复。关键不在于使用的词汇，而在于他们的设计是否会因一次错误而对客户二次收费。

### 3. “这个系统可以读取、修改和花费哪些内容？”

Ask for the边界：它可以读取哪些记录、可以执行哪些操作、哪些情况下需要人工批准，以及什么机制可以阻止循环在你的信用卡上整夜运行。

然后询问该边界在哪里被强制执行。仅仅在提示中告诉模型要小心，只是由策略文本构成的防火墙——意图在，强制执行却没有。让他们画出边界并提出一个尝试跨越它的测试。

在此过程中加入数据泄露的讨论：哪些信息会发送给模型提供商，哪些会写入日志，谁可以读取这些日志。 “我们记录所有内容”是一场合规对话的前奏。

### 4. “哪部分你会在没有 LLM 的情况下构建？”

一个有能力的工程师可以把 AI 从自己提案的某些部分剔除。资格规则、算术运算和权限检查都有乏味的实现方式，永远不会产生幻觉。解释一个沮丧的客户到底想表达什么则不同。

询问模型在该工作流中为你提供了什么价值，以及哪些证据可以证明额外的失败面是合理的。如果图中每个框都需要一个代理，要求他们给出一个更小的图。

### 5. “谈谈你放弃的某个方案。”

倾听导致他们改变主意的观察点。用户想要搜索，而不是聊天。更贵的模型降低了整体处理成本。该功能不值得上线，他们也会这么说。

一次坦诚的负面结果胜过精心包装的成功案例，因为成功案例很少揭示决策规则。询问他们停止了什么，以及花了多长时间才停止。

## 为一次小型实作付费

使用有界、付费的合成数据练习。提前发送任务简述和评分标准——你招聘的是判断力，而不是被埋伏的能力。让候选人使用他们在工作中会用的工具，包括 AI，然后让他们解释并验证产生的结果。

一个面向应用工程师的示例 90 分钟会话：

> 你接手一个支持助理，它会起草回复并提出退款。这里有十二条合成工单、一个简短的政策文档以及四次记录的运行结果。某个答案引用了我们三月已下线的政策。某个退款请求超时。某条工单请求获取另一位客户的信息。请判断我们是否要扩大试点，并给出一个小的改进或测试方案。

十五分钟澄清目标，四十五分钟深入分析，三十分钟解释推荐。提供一个预置环境，避免练习暗中变成 `npm install` 的测试。满足可访问性需求，并保持所有候选人条件一致。

你要观察他们提出了哪些问题、打开了哪些证据、首先关注了哪些风险。他们是否注意到十二条工单不足以建立可靠性？他们能否只修复一个狭窄的问题而不声称系统已经完好？他们能说出下一周应该做什么吗？

添加了针对重复退款的失败测试的候选人，可能比交付了华丽聊天界面的候选人透露更多信息。

对所有应聘者使用相同的核心问题和相同的评分标准——这正是美国人事管理局 [结构化面试指南](https://www.opm.gov/policy-data-oversight/assessment-and-selection/structured-interviews/) 背后的基本框架，目的是让你的面试小组比较候选人而不是凭感觉。让练习贴近真实工作。工作样本与自由咨询之间的界限比大多数招聘经理想象的要窄，候选人也能从房间另一侧感受到这一点。

## 招聘评分卡

复制此内容到面试文档中。在与你会面任何候选人之前，**先就每个维度的要求水平达成一致**，因为一旦你喜欢上某个人，评判标准就会随之改变。每位面试官在复盘前独立打分，并为每个评分附上具体观察。

使用 **1 = 缺乏支撑或实质性错误**，**2 = 在大量指导下可行**，**3 = 在岗位职责范围内合理**，**4 = 判断稳健并有验证证明**。当面试未能产生证据时，使用 **N/O = 未观察到**。N/O 表示存在待填补的空白，而不是可以直接算作零平均。

| 维度 | 能获得 3 分的证据 | 分数 / 观察到的证据 |
| --- | --- | --- |
| 技术判断 | 选择了相称的设计并解释了被否决的备选方案 | ___ / ___ |
| 产品判断 | 定义了用户结果、基准以及停止的理由 | ___ / ___ |
| 评估 | 提出具代表性的案例并检查结果，而非仅给出流畅的答案 | ___ / ___ |
| 生产纪律 | 处理局部故障、恢复、监控、成本和延迟 | ___ / ___ |
| 安全 | 识别敏感数据并说明可执行的访问和支出限制 | ___ / ___ |
| 沟通 | 直白陈述不确定性并向决策者解释其后果 | ___ / ___ |
| 所有权 | 将自己的工作与团队区分开，并跟进故障直至解决 | ___ / ___ |

这是一份决策辅助工具，而非经验证的工作表现预测器。请根据你的岗位进行校准，并在新人入职后与实际情况对照检查——否则你只是在调校一个从未打分的评审者。

对于需要独自负责生产的岗位，我希望在每个关键维度都有可靠的证据。整体得分再高，也不能掩盖权限或恢复方面的未解决弱点；这两项往往是后期费用的根源。对于仍在成长的工程师，写下他们需要的支持以及提供支持的人员姓名。

在复盘结束时用三句话收尾：**此人能负责哪些工作？需要哪些支持？我们仍存在哪些不确定？** 若评审小组无法回答这些问题，就意味着他们即将进行一次关于执行力的四十分钟对话。

## 红旗需要再问一次

当候选人无法将自己的贡献与团队区分、把每个过去项目都描述为完整成功，或用形容词回答测量问题时要格外小心。比如 “高度准确” 必须给出分母。

其他警示信号：在问题尚未明确前就出现代理设计；运营成本没有上限；故障恢复被推给其他团队；安全完全依赖提示词。

在得出结论前，先用具体情境进行一次探查。陌生术语不代表概念缺失，很多优秀工程师只是用了不同的叫法。若有人在回答过程中自行发现错误并纠正，应予以肯定。看到相矛盾的证据后仍拒绝更新答案是致命失误——需要片刻思考则不算。

## 已经担心招聘结果？先审计工作

一个陷入困境的 AI 项目并不意味着你雇错了工程师。可能是任务本身不可能完成、数据不可用，或高层在发布会前承诺了完全自治，却从未衡量质量。

在要求重写之前，先在合适的访问控制下保存代码、配置、评估结果以及相关日志。随后明确公司实际掌控的账户、服务和 API 密钥——这往往是团队发现整个流水线跑在某人个人计费账户上的关键点。

让独立方审阅几条具代表性的工作流。哪些能正常运行？哪些会失败？哪些声明可以复现？在不确定行为仍在调查期间，限制高风险操作，并将工作划分为保留、修复和替换。

要求提供一份简短的恢复计划，包含验收测试、责任人以及决策日期。 “我们需要一个新框架” 是需要审查的提议，而非诊断结论。

## 让新员工有权让路线图失望

如果公司惩罚刚刚用六周时间挑选出的判断，那么上述所有做法都将失效。

当工程师说 “此步骤仍需人工批准” 或 “试点尚不足以支撑扩展” 时，需要有能够在他人面前倾听的领导。先为证据招聘，再把不便的发现埋藏起来，你就打造了一台为已有答案服务的昂贵机器。

因此，对于下一个 AI 岗位：先写好目标，使用评分卡，然后观察候选人如何深入处理那些不完美的地方。

你需要的是能够向你证明系统已准备就绪的人——同时也会在系统不达标的那一天，毫不犹豫地当场说明原因。
