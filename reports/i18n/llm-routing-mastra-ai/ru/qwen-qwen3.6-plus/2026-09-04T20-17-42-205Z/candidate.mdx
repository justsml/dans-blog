Большинство инженерных команд выбирают одну языковую модель и на ней застревают. Один провайдер, одна модель, все задачи. Это как нанять одного человека писать код, тексты и сдавать налоговую декларацию только потому, что он хорошо прошёл первое собеседование.

В любой момент времени одна модель лучше пишет код, другая лучше справляется с длинным и грязным контекстом, а третья — самая дешёвая и скучная рабочая лошадка для классификации. Названия меняются. Форма проблемы остаётся прежней. Относиться к одной модели как к универсальному решению — значит либо переплачивать за простые задачи, либо получать посредственные результаты на специализированных.

Я видел, как команда сливала тысячи долларов, прогоняя анализ тональности через модель за 30 долларов за миллион токенов, хотя модель за полдоллара справилась бы ничуть не хуже. Простое форматирование JSON, базовые задачи классификации — всё шло через их премиум-провайдера. Грелся только счёт от AWS.

Есть способ лучше, и он не особенно сложен.

## Делегирование вместо фанатизма

Что если маршрутизировать запросы к той модели, которая действительно лучше всего подходит для конкретной задачи? Используйте дорогой флагман для сложных задач, а простой парсинг и форматирование отдавайте чему-то подешевле. Получите преимущества нескольких провайдеров без необходимости вручную жонглировать ими в кодовой базе.

Mastra позволяет собрать именно такую систему. Вы настраиваете специализированных агентов для разных типов задач, а затем создаёте агента-супервизора, который решает, какой специалист должен обработать каждый запрос. Идентификаторы моделей ниже используют текущий строковый формат `provider/model` от Mastra; это примеры, а не рейтинг лидеров. Замените их на актуальные модели, которые проходят ваши eval-тесты и укладываются в бюджет.

Представьте это так: в вашей команде три специалиста.

```typescript
// ./src/mastra/index.ts
import { Mastra } from '@mastra/core/mastra';
import { Agent } from '@mastra/core/agent';
import { Memory } from '@mastra/memory';
import { LibSQLStore } from '@mastra/libsql';

export const claudeAgent = new Agent({
  id: 'claude-agent',
  description: 'Handles implementation, refactoring, and code review tasks.',
  instructions: 'You are an expert engineer. Write bugs? You are fired.',
  model: process.env.CODE_MODEL ?? 'anthropic/claude-sonnet-4-6',
});

export const geminiAgent = new Agent({
  id: 'gemini-agent',
  description: 'Handles long-context synthesis and messy document analysis.',
  instructions: 'You are a creative writer. Be weird.',
  model: process.env.LONG_CONTEXT_MODEL ?? 'google/gemini-2.5-pro',
});

export const gptAgent = new Agent({
  id: 'gpt-agent',
  description: 'Handles routine classification, formatting, and general Q&A.',
  instructions: 'You are a helpful assistant. Be boring.',
  model: process.env.GENERAL_MODEL ?? 'openai/gpt-5-mini',
});
```

У каждого своя задача, и поле `description` участвует в маршрутизации. Ваш агент для кода должен быть моделью, которая проходит специфичные для вашего репозитория eval-тесты. Агент для длинного контекста должен справляться с вашими реальными документами, не превращая середину в кашу. Общий агент должен быть дешёвым, надёжным и скучным в самом лучшем смысле этого слова.

Вот тут начинается самое интересное. Вы добавляете лёгкого супервизора, который работает как интеллектуальный прокси:

```typescript
export const supervisorAgent = new Agent({
  id: 'supervisor-agent',
  name: 'The Boss',
  instructions: `You route work to the right specialist.
  Delegate coding work to claude-agent.
  Delegate long-context document work to gemini-agent.
  Delegate routine classification and formatting to gpt-agent.
  Do not do specialist work yourself unless delegation is unnecessary.`,
  model: process.env.ROUTER_MODEL ?? 'openai/gpt-5-mini',
  agents: {
    claudeAgent,
    geminiAgent,
    gptAgent,
  },
  memory: new Memory({
    storage: new LibSQLStore({ id: 'router-memory', url: 'file:mastra.db' }),
  }),
});

export const mastra = new Mastra({
  agents: { supervisorAgent, claudeAgent, geminiAgent, gptAgent },
});
```

Сам супервизор может работать на лёгкой модели, потому что его задача — в основном решать, куда направить трафик. Вы не платите премиум за то, чтобы понять, какую другую премиум-модель использовать. Измеряйте и это: плохой слой маршрутизации незаметно превращает экономию в ошибки маршрутизации.

Когда кто-то просит реализовать сортировку пузырьком, роутер распознаёт это как задачу по коду и передаёт вашему кодовому специалисту. Промпт на креативное письмо? Отправляйте модели, которую вы выбрали за стиль и широту. Фактологический вопрос об исторических событиях? Маршрутизируйте в общий агент, в идеале с подключением retrieval, когда важны свежесть данных или ссылки на источники.

## Практические преимущества

**Экономическая эффективность важнее, чем кажется.** Небольшая модель-роутер, принимающая решения о делегировании, стоит долю от стоимости прогона каждого запроса через вашего самого дорогого провайдера. Со временем, особенно на масштабе, это выливается в реальные деньги. Вы платите за тяжёлую вычислительную мощь только тогда, когда она действительно нужна.

**Качество растёт, когда вы подбираете модель под задачу.** Лидер меняется от месяца к месяцу, в зависимости от задачи и формы промпта. Именно поэтому слой маршрутизации должен опираться на ваши eval-тесты, а не на то, какая модель выигрывала в Twitter на неделе написания интеграции.

**Отказоустойчивость становится возможной, но не автоматической.** Приведённый выше супервизор не повторяет запрос к упавшему провайдеру через другого агента и сам зависит от OpenAI при принятии решений о маршрутизации. Если переключение между провайдерами (failover) критично, добавьте явную политику повторов и фоллбэков в код приложения, держите резервный роутер у другого провайдера и тестируйте сценарии отказов. Набор агентов не становится circuit breaker только потому, что у моделей разные логотипы.

Речь не о том, чтобы выдумывать сложности ради сложности. Речь о построении систем, которые имеют смысл и с финансовой, и с технической точки зрения. Вы же не станете бить одним и тем же молотком по всему на стройке, и, вероятно, не стоит использовать одну и ту же языковую модель для всех задач ИИ.

Прелесть этого подхода в том, что вашему приложению не нужно городить лабиринт из ветвлений. Вы по-прежнему вызываете одного агента. Сложность выбора модели для конкретной задачи сосредоточена в одном месте, настраивается один раз, а не размазана по всей кодовой базе в виде кучи условных конструкций.
