> Обеспечение безопасности ключей API и токенов **критически важно**!

Одна ошибка может привести к потере контроля над сервером и данными хакерами!

Но определять, нужно ли скрывать конкретный токен, не должно быть так сложно — даже опираясь на официальную документацию!

Ситуация усугубляется мешаниной из встречающихся смежных терминов: _токены_, _ключи_, _учётные данные_, _секреты_, _частные_ и _публичные_.

Давайте переформулируем это как различие между `секретными` и `несекретными`.

* 🔒 [`Секретные ключи`](#-секретные-ключи) ОБЯЗАНЫ оставаться скрытыми. В общем случае они никогда не должны покидать ваш приватный сервер (или сервис — например, heroku, netlify или travis-ci).
* 🌍 [`Несекретные ключи`](#-несекретные-ключи) описывают строки, которыми можно свободно делиться и включать в браузерные запросы.

## 🔒 Секретные ключи

** ‼️ Важно:** Секретные ключи **ОБЯЗАНЫ** игнорироваться Git'ом _И_ отсутствовать во всём браузерном коде. [_Как использовать dotenv_](#как-безопасно-обрабатывать-секреты)

<br />

_Как понять, что имеешь дело с секретным ключом?_

<br />

**👍 Эмпирическое правило:** серверы, возвращающие `CORS-ошибки`, не поддерживают работу из браузера. Это сильный признак того, что необходимо **проксировать** сервис, обращаясь с ним как с `секретным`.

**👍 Эмпирическое правило:** дорогие сервисы (почти) всегда следует проксировать или скрывать.

**👍 Эмпирическое правило:** если вы выполняете операцию записи (**загрузка файла, вставка строки в БД**), вы, вероятно, имеете дело с `secret keys`.

<br />

**_Случаи использования и особенности:_** `Secret` keys

- Долгосрочная авторизация (учётные данные, access токены, JSON Web Tokens)
- Краткосрочная авторизация (OAuth токены, хранилище сессий)
- Доступ к платным/дорогим сервисам (для авторизации, геокодирования, хранения файлов и т.д.)
- Приватная часть публичной/приватной пары (RECAPTCHA, Stripe, Auth0)
- Учётные данные сервисов (Email/SMTP, LDAP/Службы каталогов)
- Шифрование данных и проверка целостности

### Контрольный список: Безопасная обработка секретов

#### Краткий обзор

Выполните следующие шаги, чтобы **исключить секреты из вашего кода:**

- [ ] Замените жёстко заданные ключи переменными окружения. Например, `process.env.API_SECRET`
- [ ] Используйте библиотеку типа [`dotenv`](https://github.com/motdotla/dotenv#dotenv) вместе с файлом `.env`. Добавьте ранее жёстко заданные секреты в файл `.env`.
- [ ] Добавьте строку `.env` в ваш файл `.gitignore`!

> **НЕ** создавайте файл `.env` на развёрнутых серверах. Используйте инструмент управления переменными окружения, предоставляемый вашим хостинг-провайдером (например, [Heroku](https://devcenter.heroku.com/articles/config-vars), Netlify, AWS EC2): **панель управления или командную строку.**

## 🌍 `Non-secret keys`

**👍 Эмпирическое правило:** когда ключ должен быть отправлен в браузер в коде или встроен (например, через тег `<script src="https://my-api/?apiKey=123-abc-456">`), **это определенно `non-secret`**. Типичный пример — Google Maps.

<br />

**_Случаи использования и особенности:_** `Non-secret` keys

- Краткосрочный доступ (ID сессий пользователей, JSON Web Tokens)
- Ограничение доступа к API по приложению/разработчику (для авторизации, геокодирования и т.д.)
- Публичная часть публичной/приватной пары (RECAPTCHA, Stripe, Auth0)
- ID аналитики

#### ✅ Обработка несекретных ключей:

> **Безопасно жестко задавать несекретные (публичные) ключи!**

Для упрощения долгосрочного управления используйте общий `config.js` в вашем приложении.

**Пример:**

```js
// config.js
module.exports = {
  googleMapsKey: '123-abc'
};
```

```js
// load-map.js
const config = require('./config.js');
const key = config.googleMapsKey;
const src = `//maps.googleapis.com/maps/api/js?key=${key}`;
// ...
```
