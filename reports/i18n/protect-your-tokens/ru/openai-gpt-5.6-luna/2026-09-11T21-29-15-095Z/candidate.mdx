## Когда нужно защищать токены?

> Защита API-ключей и токенов **критически важна**!

Одна ошибка может привести к тому, что вы потеряете контроль над сервером и данными, отдав их злоумышленникам!

Определить, нужно ли скрывать конкретный токен, не должно быть настолько сложно — даже по официальной документации!

Ситуацию часто усугубляет суп из связанных терминов, с которыми вы столкнётесь: _токены_, _ключи_, _учётные данные_, _секреты_, _приватные_ и _публичные_.

Давайте переформулируем это как различие между `secret` и `non-secret`.

* 🔒 [`Секретные ключи`](#-секретные-ключи) ДОЛЖНЫ оставаться скрытыми. Как правило, они НИКОГДА не должны покидать ваш приватный сервер (или сервис — например, heroku, netlify или travis-ci).
* 🌍 [`Несекретные ключи`](#-несекретные-ключи) — это строки, которыми можно свободно делиться и включать их в запросы из браузера.

## 🔒 `Секретные ключи`

** ‼️ Важно:** `Секретные ключи` **ДОЛЖНЫ** игнорироваться Git _И_ исключаться из любого браузерного кода. [_Как безопасно работать с dotenv_](#-как-безопасно-работать-с-секретами)

<br />

_Как понять, что вы имеете дело с `Секретным ключом`?_

<br />

**👍 Практическое правило:** серверы, которые возвращают `CORS errors`, не поддерживают работу из браузера. Это убедительно указывает на то, что вы **ДОЛЖНЫ** проксировать сервис, обращаясь с ним как с `secret`.

**👍 Практическое правило:** дорогостоящие сервисы почти всегда следует проксировать или скрывать.

**👍 Практическое правило:** если выполняется операция записи (**загрузка файла, добавление строки в БД**), возможно, вы имеете дело с `secret keys`.

<br />

**_Варианты использования и возможности:_** ключи `Secret`

- Долгосрочная авторизация (учётные данные, токены доступа, JSON Web Tokens)
- Краткосрочная авторизация (токены OAuth, хранилище сессий)
- Доступ к платным/дорогостоящим сервисам (аутентификация, геокодирование, файловое хранилище и т. д.)
- Приватная часть пары «публичный/приватный» (RECAPTCHA, Stripe, Auth0)
- Учётные данные сервисов (Email/SMTP, LDAP/Directory Services)
- Шифрование данных и проверка их целостности

### Чеклист: безопасная работа с секретами

#### Кратко

Выполните следующие шаги, чтобы **убрать секреты из кода:**

- [ ] Замените жёстко заданные ключи переменными окружения. Например, `process.env.API_SECRET`
- [ ] Используйте библиотеку вроде [`dotenv`](https://github.com/motdotla/dotenv#dotenv) вместе с файлом `.env`. Перенесите ранее жёстко заданные секреты в файл `.env`.
- [ ] Добавьте строку `.env` в файл `.gitignore`!

> **НЕ** создавайте файл `.env` на серверах, где развёрнуто приложение. Используйте предоставляемый вашим хостинг-провайдером (например, [Heroku](https://devcenter.heroku.com/articles/config-vars), Netlify, AWS EC2) инструмент управления переменными окружения: например, **панель управления или командную строку.**

## 🌍 `Non-secret keys`

**👍 Практическое правило:** если ключ обязательно нужно передать браузеру в коде или встроить в него (например, через тег `<script src="https://my-api/?apiKey=123-abc-456">`), это однозначно `non-secret`. Типичный пример — Google Maps.

<br />

**_Варианты использования и возможности:_** ключи `Non-secret`

- Краткосрочный доступ (идентификаторы пользовательских сессий, JSON Web Tokens)
- Ограничение доступа к API для приложения/разработчика (аутентификация, геокодирование и т. д.)
- Публичная часть пары «публичный/приватный» (RECAPTCHA, Stripe, Auth0)
- Идентификаторы аналитики

#### ✅ Работа с non-secret:

> **Жёстко задавать non-secret (публичные) ключи безопасно!**

Сделайте долгосрочное сопровождение проще с помощью общего файла `config.js` для приложения.

**Пример:**

```js
// config.js
module.exports = {
  googleMapsKey: '123-abc'
};
```

```js
// load-map.js
const config = require('./config.js');
const key = config.googleMapsKey;
const src = `//maps.googleapis.com/maps/api/js?key=${key}`;
// ...
```
