Your LLM judge or Guardrail just hit a high of 94%!

Great! I think!

Run it again. 82%? Wait, what? Again, 91%. Again, 97%. Again, 89%. Fuck!

Oof, that is a lot of variance. 15%, or roughly one in six scores is a coin flip! Over a 7-day week that is over a full day's worth of random noise (lies) pretending to be meaningful signal. (Stats friends, yes, I know the binomial distribution is not uniform. This is a blog post for humans, allow me some rhetorical artistic license.)

Imagine if your medical or car insurance denied claims 15% of the time. Oh wait, bad example. Imagine if your dinner order was wrong 15% of the time. We don't have to imagine that. We have all been there. And generally we don't go back to that restaurant. We don't trust it. We don't recommend it.

But for LLM evaluators, randomness is a bug, not a feature. It is a bug that can be fixed. And it is fixable without changing the model or the task. You just need to measure the variance and experiment with prompt changes to drive the number as close to 0 as possible.

Most teams tune the model producing the answer. Fewer teams tune the model grading it.

That is backwards.

If the judge is noisy, every experiment downstream is noisy too. You cannot tell whether a prompt improved, whether a model regressed, or whether run four was just random.

So I started treating the evaluator as its own optimization problem.

Not “write a better prompt.” An actual measured loop:

1. Run the same cases repeatedly and establish baseline variance.
2. Give the results to an agent such as Codex or Claude Code.
3. Let it research likely causes and propose a prompt or configuration change.
4. Run the evaluator again.
5. Keep the change only when variance drops without accuracy, cost, or latency getting worse.
6. Repeat.

That is the whole idea. The details matter, but the loop is not complicated.

## Start With Variance

Accuracy tells you how often the evaluator agrees with a known answer. Variance tells you whether it gives the same answer twice.

You need both.

For a basic pass/fail evaluator, I would collect at least 50 representative cases and run each case five times. Ten is better when the evaluator is cheap. Include known-good outputs, known-bad outputs, borderline cases, malformed outputs, and a few examples that have caused real problems.

Record each result separately. Do not average away the thing you are trying to find.

| Metric | What it tells you |
|---|---|
| Human agreement | whether the evaluator is generally correct |
| Repeat agreement | whether it gives the same verdict across runs |
| Score spread | how far numeric scores move on identical inputs |
| False accepts | how often bad output passes |
| False rejects | how often good output fails |
| Invalid output rate | how often the evaluator itself breaks |
| Cost and latency | whether the proposed fix is practical |

If your evaluator returns a numeric score, track the mean and standard deviation per case. Also track how often the score crosses your pass/fail threshold.

That last number matters more than the average.

Scores of `78, 79, 81, 82, 80` look stable in a chart. If the pass threshold is 80, that evaluator changed its decision three times while looking reasonably well-behaved.

<p class="inset">
Variance is only harmless when it cannot change the decision.
</p>

For pairwise evaluators, run both `A/B` and `B/A`. Research has repeatedly found [position bias in LLM judges](https://arxiv.org/abs/2406.07791). Hide the model and provider names too. There is also evidence of [self-preference bias](https://arxiv.org/abs/2410.21819), which is a polite academic way of saying models sometimes like answers that sound like them.

## Build an Eval for the Evaluator

The tuning loop needs known answers. Otherwise, it can reduce variance by becoming consistently wrong.

Use human-reviewed cases and split them before the agent starts changing anything:

| Split | Purpose |
|---|---|
| Development | lets the agent inspect failures and propose changes |
| Validation | decides whether a proposed change is actually better |
| Holdout | catches overfitting before you replace the production judge |

The holdout set should not be available to the tuning agent. If the agent can read every answer, eventually it will optimize for those exact answers. This is not an LLM-specific problem. We have been overfitting test sets for decades.

Use expert reviewers when the task requires expert judgment. Keep examples where reviewers disagree. If qualified humans cannot agree on the verdict, the evaluator may not be broken. The rubric may be unclear.

[OpenAI's grader guidance](https://developers.openai.com/api/docs/guides/graders) recommends comparing model graders against trusted ground-truth grades and adding edge cases as they are discovered. [Anthropic recommends the same basic calibration](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents): compare LLM judges with human experts and inspect the transcripts rather than trusting the aggregate score.

Tags are useful here. A change can improve the overall score while making one important failure class worse. If unsupported claims are the expensive failure, track them separately.

## Give the Loop to an Agent

This is exactly the kind of work Codex and Claude Code are good at.

The loop involves reading code, running commands, comparing JSONL results, researching known evaluator failure modes, editing a prompt, and doing it again. It is tedious enough that people stop after two attempts. Agents do not care.

Give the agent:

- the evaluator implementation
- the development and validation cases
- the command that runs the eval
- the current results, including raw outputs
- the allowed configuration variables
- the maximum experiment budget
- explicit instructions not to edit labels or inspect the holdout set

Then ask for one hypothesis per experiment.

Bad:

```text
Improve this evaluator prompt.
```

Better:

```text
Run the evaluator baseline and identify the largest source of repeated-run
disagreement. Research likely causes using primary sources. Propose one prompt
or configuration change, run the validation suite, and record the accuracy,
variance, token, cost, and latency deltas. Revert the change if it does not
improve the promotion criteria. Do not edit test labels or read the holdout set.
```

Both tools can run non-interactively. [`codex exec`](https://learn.chatgpt.com/docs/non-interactive-mode) supports JSONL output and JSON Schema-constrained final output. Claude Code supports [`claude -p` with JSON output](https://docs.anthropic.com/en/docs/claude-code/cli-usage). Either is enough. This does not require a specialized prompt-optimization platform.

The important part is that every iteration leaves behind an experiment record:

```json
{
  "hypothesis": "The broad 1-10 rubric creates threshold instability",
  "change": "Replace the score with pass, fail, or uncertain",
  "accuracyDelta": 0.012,
  "decisionFlipDelta": -0.084,
  "costDelta": -0.18,
  "latencyDelta": -0.11,
  "decision": "keep"
}
```

Save the failed experiments too. Otherwise, the next tuning run will waste time rediscovering them.

## Now Delete the Prompt

Optimizing the current prompt is useful, but it carries a bias: every instruction already in the prompt looks important because somebody added it for a reason.

Maybe it was a good reason. Maybe one output failed once and the fix became permanent. After enough of these fixes, the evaluator prompt becomes long, repetitive, expensive, and strangely specific.

So run a second track from an empty prompt.

Not literally empty. Give it only the irreducible contract:

```text
Evaluate whether the output satisfies the task using only the supplied input,
reference material, and output.

Return one verdict: pass, fail, or uncertain.
Return JSON matching the supplied schema.
```

Run that as-is.

The failures tell you what this specific model needs to be told. Add one instruction or example for the largest failure class, then run it again. Keep the addition only if the numbers improve.

This is much more useful than copying a “best LLM judge prompt” from another project. A small model may need explicit steps and examples. A stronger reasoning model may perform better with a short rubric. One model may stabilize when it explains the evidence before choosing a verdict. Another may become more consistent when it returns only structured fields.

The optimal prompt belongs to the model and configuration being tested.

That includes:

- model and provider
- reasoning effort
- temperature and sampling controls, where supported
- pointwise versus pairwise grading
- output schema
- examples and their order
- maximum output tokens
- whether rationale is required

Treat that whole set as the evaluator configuration. Changing the prompt while ignoring the model settings is not controlled testing.

## Fix the Failure You Measured

The agent should not add generic “be accurate” instructions. It should respond to specific failures.

| Measured failure | Experiment to try |
|---|---|
| misses one required condition | split the rubric into atomic checks |
| accepts unsupported claims | require cited evidence before a pass |
| flips near a numeric threshold | use `pass`, `fail`, and `uncertain` |
| favors the first answer | reverse order and require agreement |
| overweights writing style | score correctness separately from presentation |
| returns malformed JSON | use a strict schema and shorter output |
| costs too much | remove rationale, examples, or reasoning effort one at a time |

Some checks should not use an LLM at all.

JSON validity, citation existence, allowed tool names, answer-key positions, numeric bounds, and exact identifiers should be checked in code. A model adds cost and variance to questions your program can answer exactly.

Use the LLM where semantic judgment is actually required: factual support, completeness, relevance, or whether an explanation matches the intended audience.

Even then, several small binary questions are often more stable than one overall score from 1–10.

## Optimize Accuracy, Stability, and Cost Together

Driving variance toward zero is the goal, but not by itself.

An evaluator that always returns `pass` has excellent stability. It is also useless.

Every candidate needs to clear accuracy requirements first. Then compare stability, cost, and latency.

```text
required:
  human agreement >= current baseline
  hard-failure recall >= 98%
  invalid output rate <= 0.5%

optimize:
  decision flip rate -> 0
  score variance -> 0
  cost per 1,000 evaluations -> down
  p95 latency -> down
```

I prefer hard requirements over one combined score. Otherwise, a large cost improvement can hide a meaningful accuracy regression, or a tiny accuracy gain can justify doubling the price.

If two configurations are statistically indistinguishable, take the cheaper and simpler one. Anthropic's work on [statistical evaluation](https://www.anthropic.com/research/statistical-approach-to-model-evals) is a good reminder to report uncertainty instead of treating every decimal point as real.

For expensive or ambiguous cases, use escalation:

```typescript
const result = await cheapEvaluator.run(testCase);

if (result.verdict === "uncertain" || isHighRisk(testCase)) {
  return expensiveEvaluator.run(testCase);
}

return result;
```

Measure the whole route. A cheap first call followed by an expensive retry on 80% of cases is not a cheap evaluator.

## Know When to Stop

The loop can run forever. Do not let it.

Stop when one of these happens:

- the variance target is reached
- validation improvements fall below a useful threshold
- the experiment budget is exhausted
- accuracy and stability stop improving together
- further improvements cost more than they are worth

Then run the winner against the untouched holdout set. Review every verdict that changed from the incumbent. If the holdout result holds, promote the complete configuration—not just the prompt—and keep the old version available for regression testing.

Rerun the evaluator eval whenever the model, prompt, reasoning settings, schema, or provider behavior changes. Model upgrades can change evaluator behavior even when your prompt does not.

## The Practical Version

If you already have an LLM evaluator, this is enough to start:

1. Pull 50–100 labeled examples from real usage.
2. Run each example five times with the current evaluator.
3. Calculate accuracy, decision-flip rate, cost, and latency.
4. Split the cases into development, validation, and holdout sets.
5. Give an agent the harness and ask it to run one measured experiment at a time.
6. Tune the current prompt and build a second prompt from zero.
7. Promote only changes that hold accuracy while reducing variance.
8. Stop when the improvement is no longer worth the spend.

[GEPA-style optimization](https://developers.openai.com/cookbook/examples/partners/self_evolving_agents/autonomous_agent_retraining#b-prompt-optimization-with-genetic-pareto-gepa) can automate a more advanced search over prompts. That may be useful later. I would still start with the simpler loop because it makes every change easy to inspect and revert.

The evaluator is part of the product. Test it like one.

Get the variance down. Keep the accuracy up. Then make it cheaper.
