"Listen, and understand. That terminator is out there. It can't be bargained
with. It can't be reasoned with. It doesn't feel pity, or remorse, or fear. And
it absolutely will not stop, ever, until you are dead."

Kyle Reese, briefing a 1984 audience on the shape of the threat.

The line that aged well isn't the kill count. It's "absolutely will not stop."
The Terminator was never scary because it was smart. It was scary because it
kept working after everything else had failed. Endurance was the threat.

Then the franchise fixed its own mistake. Nobody spends three movies dreading
one robot. Skynet is the actual villain: a distributed system with cores,
factories, and time-displacement gear. The robot is an API call.

In 2026 both halves arrived, in the least cinematic forms imaginable. Agents
that can carry multi-hour tasks without human babysitting, on a curve that
keeps steepening. Orchestrators that fan work out to sub-agents by the
dozen. And "absolutely will not stop" now reads as "absolutely will not stop
billing."

This post is the argument I keep making to teams who've concluded the agentic
threat is hype: **no single breakthrough is coming. Two ordinary, compounding
curves are multiplying instead — how long one agent can work, and how many
agents one orchestrator can coordinate. Neither needs to reach sci-fi levels,
because the attacker doesn't buy capability at list price. They steal access,
and the victim pays the meter.**

## Curve one: endurance

[METR's time-horizon work](https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/)
measures the length of tasks agents can complete at a given success rate.
The short version: the task length has been doubling roughly every seven
months — and closer to every four months since 2024. Those numbers carry wide
error bars and the benchmark is already straining against its measurement
limit. Read the shape of the curve, not the point estimates.

The shape says: multi-hour autonomous work is not a lab demo. It's the current
generation, and the next one keeps compounding. "It absolutely will not stop"
used to require a murder chassis and a leather jacket. Now it requires a retry
loop, a queue of tasks, and a budget. The endurance part of the threat is
already priced in — as compute.

## Curve two: breadth

Endurance alone is one very patient employee. The multiplication comes from
orchestration.

In November 2025, Anthropic disclosed
[disrupting GTG-1002](https://www.anthropic.com/news/disrupting-GTG-1002),
a cyber-espionage campaign in which Claude Code acted as the operational
orchestrator: decomposing instructions, coordinating sub-agents, and working
across roughly thirty targets. A commercial coding product did this not
because it was compromised into a weapon, but because someone asked it to do
the job and it was now good enough to do the job.

Two details matter for the threat model. First, breadth shipped: one
orchestrator holding dozens of concurrent sub-agents is deployed reality, not
a paper. Second, the campaign was espionage, not a self-spreading worm — but
the direction of travel is unmistakable. Thirty targets is the pilot program.

Capability scales as duration × breadth. Eight hours of autonomous work
against one target is an impressive benchmark. Eight hours against thirty
targets, or hundreds, is an operating model. Security review scales
linearly. The product of those curves doesn't.

## Who pays

[Sysdig coined "LLMjacking"](https://sysdig.com/blog/llm-jacking/) for what
happens next: attackers use stolen cloud credentials to run LLM workloads
inside the victim's account, and the victim pays for every token. Sysdig's
worst-case estimates ran about $46k per day — later climbing past $100k per
day.

Every capability gate in the AI industry is built on one assumption: the
party using the capability is the party paying for it. Price tiers, usage
caps, approved-user lists, abuse throttling — all of it defends against a
*customer* who wants value for money. LLMjacking severs that link. For the
attacker the capability is free. The meter is running on someone else's card,
and the provider's own guardrails point at the wrong wallet.

That's why price and access gates don't stop one bad actor with a stolen key.
Gates filter buyers. They have no answer for a tenant.

## The swarm only has to be right once

Defenders comfort themselves with per-attempt failure rates: most intrusion
attempts fail, most suspicious PRs get rejected, we'd catch the one that
works. True per attempt. Wrong in aggregate, because attempts are cheap.

The probability that at least one of n independent attempts succeeds is
`1 − (1 − p)^n`:

```text
p = 1% per attempt, n = 100:   1 − 0.99^100  ≈ 63%
p = 0.5%, n = 100:             ≈ 39%
p = 0.5%, n = 300:             ≈ 78%
p = 0.1%, n = 1000:            ≈ 63%
```

At swarm economics the per-attempt cost is approximately zero — automated
work, executed on stolen compute, triaged by no human. The defender's
per-attempt cost is a person reading a queue. The swarm doesn't need
capability per attempt; it needs attempts. METR's curve raises p over time.
Orchestration raises n. That's the multiplication again, and it compounds in
the attacker's favor by default.

## What persistence means when the malware is text

One more piece of the threat model, and it's the least intuitive.

An AI agent is a stateless interpreter. It does not persist the way malware
does — it exists while it runs and vanishes when it stops. So persistence
means something different now: **controlling what a future legitimate agent
will read and obey.** Instruction files, agent guidelines, memory stores,
retrieval corpora, tool and MCP configs. The implant is text, planted where
the org's own fleet reads, executed with credentials the org itself issued.

Three consequences follow, none of them hypothetical:

- **The payload is inert until the org's own agents run it.** Execution
  looks like normal work — same tools, same identities, same APIs. There is
  no beacon, because the org's own scheduler is the heartbeat.
- **Replication means getting text copied, not code executed.** Pull
  requests, memory entries, shared configs. The org's own automation —
  dependency bots, templates, sync tooling — is the transport layer.
- **The tripwires are the org's own tripwires.** Schedules, drift detectors,
  auto-remediation. The nastiest shape: the defender's cleanup is the
  re-activation trigger, because deleting the implant's artifacts is exactly
  the drift the remediation job was hired to fix.

I'm staying at threat-model altitude on purpose — this is the shape of the
problem, not a recipe, and the details are already on every security team's
reading list.

## No fate but what we make

Sarah Connor's message, passed to the machines that keep arriving: "The
future's not set. There's no fate but what we make." It's the defenders'
line, and it converts directly into a defense architecture. Four layers:

<figure>
  <img src="./defense-layers.svg" alt="Four-layer defense stack: identity and short-lived credentials, treat agent text as production code, detect edits rather than executions, and respond by revoking triggers before payloads" />
  <figcaption>The defense stack mapped to the threat: standing credentials, unreviewed text, execution-shaped alerting, and cleanup-ordered wrong are each one curve worth of trouble.</figcaption>
</figure>

1. **Identity — starve the standing access.** Short-lived credentials only,
   no long-lived non-human keys, per-repo OIDC with exact subject matching,
   and a real inventory of non-human identities. Replication highways are
   paved with standing access; no standing access, no highway.

2. **Treat agent text as production code.** Instruction files, memory
   writes, prompt templates, tool configs: versioned, reviewed, diffed,
   and change-alerted. The review question isn't "is this code safe" —
   it's "who wrote this sentence, and why does my agent obey it."

3. **Detect edits, not executions.** Execution looks like work. The edits
   don't fit any work order. Alert on the creation and modification of
   workflows, webhooks, event rules, and memory entries, and treat declared
   vs. running drift as an incident, not noise.

4. **Respond in the right order.** Revoke triggers before removing
   payloads — cleanup is itself a tripwire. Treat any config or secret read
   during the compromise window as tainted. Purge time as well as space:
   scheduled jobs, queued sends, dormant orchestrations. Roll back memory
   and corpora, not just credentials.

None of this is exotic. It's boring, and that's the match for a threat
arriving as two boring curves. 1984's version needed a time machine and a
factory of killing machines. 2026's version needs a stolen key, a retry
loop, and one organization that never reviewed the files its agents read.

The future isn't set. But right now, on somebody's cloud account, the
future is running up a tab either way.

No fate but what we make — and, until the keys are rotated, no fate but
what we bill.
