When an agent's plan misses something, the reflex is to buy a smarter agent.

New model drops. Bigger context. Higher tier. Turn effort to `xhigh`. Pay the frontier rate and hope the miss goes away.

Sometimes it does. Often the miss comes back wearing a nicer suit.

The plan that forgot the migration still forgets the migration. The review that checked the happy path checks it more eloquently. A smarter model looking from the same angle tends to miss the same thing.

So for most of this year I've done something cheaper. I run the same task three times, in parallel, under three different **priorities**, and then pick or merge the results. I call it the Council of Dans, because every member is me with a different obsession.

It feels like it works. "It feels like it works" is also what every placebo says.

So I built an eval to find out if I'm fooling myself.

## Personas are priorities, not costumes

"Persona" has a bad reputation, and it earned it. "You are a world-class senior engineer" is a costume. It changes the tone and very little else.

A council persona is a **priority**: an instruction about where to look first and what counts as a problem.

| Persona | Hunts for |
|---|---|
| Architect | Boundaries, contracts, invariants, migration paths |
| Ruthless Minimalist | Smallest coherent change that fully solves it |
| Detail Detective | Edge cases, state bugs, integration gaps |
| Doomsayer | Failure modes, hidden costs, unsafe rollouts |
| Security Paranoid | Auth, untrusted input, privilege boundaries |

The skill says it plainly: *persona is an execution bias, not a writing style.* The name supplies the worldview. The brief ties it to the work.

The theory is about **correlated errors**. Run one model three times with the same prompt and you get three samples from the same blind spot. Give it three different priorities and the blind spots move. The Doomsayer is bad at noticing that you built too much. The Minimalist is bad at noticing the retry storm. Neither is bad at both.

That's the theory. Here is how it could be wrong.

## Three ways I could be fooling myself

**1. It's just more samples.** Three of anything beats one of anything. Best-of-3 is a well-known trick and it needs no personas. If three identical runs plus a merge step do as well as the council, the personas are decoration.

**2. It's just role-play.** Maybe any persona helps, because a longer, more specific prompt makes the model try harder. If three personas that only change *writing style* do as well, priorities aren't the active ingredient.

**3. It's just the merge step.** The council ends with a synthesizer that re-checks every claim against the code. That's a second pass. Maybe a single run followed by "now check your own work" gets the same lift.

Any honest test has to beat all three, not just the bigger model.

## The eval

The full harness is in [`experiments/council-eval`](https://github.com/justsml/dans-blog/tree/main/experiments/council-eval). It drives the real CLIs, Claude Code and Codex, not raw API calls, because that's where I actually use this.

### Two jobs with ground truth

I didn't want a judge model deciding whether a plan "felt thorough." Both tasks have answers you can check mechanically.

**Code review with seeded defects.** Small, realistic TypeScript repos, each with a plausible PR that has 1 to 3 real defects hidden inside otherwise-good work. A missing ownership check. Refunds that can add up past the order total. A retry with no ceiling. Each defect ships with a hidden test that **fails on the PR and passes after that defect's fix**. A script enforces that, so every defect is provably real.

Some PRs are clean on purpose. They touch auth or money and look suspicious, so a reviewer that flags everything gets caught.

**Planning with hidden requirements.** A ticket plus a repo containing constraints the ticket never mentions: an ADR that says money is integer cents rounded down, a doc comment saying the payment provider rejects negative amounts, a README note that customers type codes in any case. Hidden acceptance tests encode them.

Then the plan goes to a **fixed implementer**, the same model with the same prompt for every arm, which builds from the plan alone. The hidden tests score the result.

That last part matters. Plan quality is measured by whether the plan produces working software, not by how it reads.

### The arms

Every arm runs on both Claude and Codex. "Mid" is Claude Sonnet 5.5 or GPT-6.1 Terra. "Frontier" is Claude Opus 5.5 or GPT-6 Astra.

| Arm | What runs | Tests |
|---|---|---|
| `M1` | 1 mid | Baseline |
| `F1` | 1 frontier | **Just upgrade** |
| `M1R` | 1 mid, then self-check | Is it the merge step? |
| `M3same` | 3 mid, same prompt, merged | Is it sample count? |
| `M3style` | 3 mid, style personas, merged | Is it role-play? |
| `M3council` | 3 mid, priority personas, merged | **The council** |
| `F3council` | 3 frontier, council | Does it stack? |

Rules that keep the comparison fair:

- **Same output budget.** Every final review is capped at 8 findings. A council can't win recall by listing 30 things.
- **Same synthesizer** for every merged arm, on the same tier as its members, and it never sees persona names.
- **Same effort** (`high`) for every call.
- **Frozen personas.** The persona text is copied from the skill and hashed. Nobody tunes it.
- **Isolated agents.** My own setup has the council skill installed. Each CLI runs from a clean config home with only the login shared, in a workspace outside any repo. A canary flags any uninstructed run that mentions council or persona names.

### Scoring

- **Review:** severity-weighted recall of seeded defects. A judge decides whether a finding names the *mechanism*, not just the right file. It sees anonymized findings with no arm or model attached. A second judge from the other vendor scores the same matches, and I hand-label a sample to check both.
- **Precision:** high-severity findings the judge marks as invalid, and false alarms on clean PRs.
- **Planning:** share of hidden acceptance tests that pass after the implementer follows the plan.
- **Cost:** list price from token counts, not subscription plans, so both vendors are on the same axis.

### Statistics, decided before the data

Per case, I average 3 seeds. Every comparison is paired by case, with a 95% bootstrap confidence interval, and Holm correction across the three primary comparisons:

1. `M3council` vs `F1`: does the council beat the upgrade?
2. `M3council` vs `M3same`: do priorities beat sample count?
3. `M3council` vs `M3style`: do priorities beat role-play?

There's also a prediction that could embarrass me. The review council is Detail Detective, Doomsayer, and Security Paranoid. None of them cares about performance or cost. If the gain comes from priorities, it should show up mostly in defect classes those three hunt for, and barely in performance and cost bugs. If the council gains just as much on perf bugs, the lift is "more eyes," not "different eyes."

### What would change my mind

- `M3same` ≈ `M3council`: personas are decoration. Use best-of-3.
- `M3style` ≈ `M3council`: any role-play helps. Priorities aren't special.
- `M1R` ≈ `M3council`: just make the model check its own work.
- `F1` > `M3council` at similar cost: buy the upgrade.

All four would be worth publishing. That was the bar for the design. An eval that can only confirm what you hoped for isn't an eval.

## A loop, not a vote

The eval tests the council once: three drafts, one merge, done. That's the cheap version. The way I actually use it on risky code is a loop.

The instruction to the agent is short:

```text
Ask the council to review the change.
Fix every Medium or higher finding.
Repeat until a round finds none.
```

Here's one run of that loop: [DocSlurp/doppler#51](https://github.com/DocSlurp/doppler/pull/51), a 5,500-line change to a PDF parser that reads untrusted files. Every round had at least two independent reviewers, one of them adversarial. They got the diff and the threat model, not the author's reasoning. The PR keeps the record:

| Round | What the council found (High) |
|---|---|
| 1 | Default mode flattened ordinary data tables |
| 3 | Tables holding a matrix were dropped |
| 5 | A new 64 MB cache bound lost images on honest PDFs |
| 6 | Tagged documents of ~5k pages ran out of memory |
| 8 | The fetch guard could be bypassed four ways |
| 9 | **No High.** Mediums fixed, two Lows documented |

Eight rounds found at least one High. The ninth found none.

The part I didn't expect is what the fixes looked like. They mostly **removed** code. The cache change was reverted to master. The per-page structure walk was deleted, and its bits were reserved for later. The fetch guard, after being bypassed four ways, was replaced by a design that makes no reads of its own. The reviewers kept attacking whatever the agent added, and the answer that finally held up was to not add it.

A smarter model would probably have written fewer of those Highs in round one. I doubt it would have written zero, and nothing in a single pass tells you which ones it missed. The loop's stopping rule isn't "the model feels done." It's "a reviewer with a different priority looked and came back empty."

**This is an anecdote, not evidence.** It's one PR with no control. I can't tell you whether one reviewer looping nine times would have found the same things, or whether a frontier model would have needed fewer rounds. The stopping rule also trusts the reviewers' severity labels, so a lenient council stops early and a nervous one never stops.

All of that is testable, though, and it's the obvious next arm for the eval: loop to a fixed point, capped at N rounds, on implementation tasks scored by hidden tests. Run the council loop against a single-reviewer loop and a frontier single-reviewer loop, and count rounds, cost, and what survives the hidden tests.

## Try it on your own work

The council doesn't need my harness. It needs three things:

1. **Pick priorities, not characters.** Two defaults that fit most work (Architect and Ruthless Minimalist for builders) plus one matched to the task's biggest risk.
2. **Merge with verification.** The merge step re-checks claims against the code and drops what it can't confirm. Without that you just get three times the noise.
3. **Cap the output.** Ask for the top 8 findings, not every finding.

And before you trust it, or trust a bigger model, run the boring control: the same prompt three times. If that does as well as your clever setup, your setup isn't clever.
