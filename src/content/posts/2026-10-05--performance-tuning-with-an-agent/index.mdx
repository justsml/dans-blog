Ask an agent to make a slow image grid scroll faster and it already knows the answer. It has read every blog post about it.

`content-visibility: auto`, so the browser skips off-screen cards. `will-change: transform`, so each image gets its own compositor layer. Those are the two tricks everyone writes about, so those are the two the agent reaches for first.

We tried both on [Emoji Brain](https://github.com/justsml/emoji-brain), a dense grid of selectable stickers where some of them dance. Broader containment tripled the p95 frame gap during rapid scroll reversals. Layer promotion on every image made the software renderer slower. Both changes sounded plausible, and both came with confident explanations. Neither came from looking at where the time went.

The fix that worked came from a trace. Raster dominated the scroll. 92 of the 402 stickers were animated WebPs, and an animated image invalidates its compositor tile on every frame. With dozens on screen, the grid could never keep a cached raster. Drawing a still first frame until hover cut raster time from 1,859 ms to 844 ms, and the payload for those 92 stickers dropped from 5.45 MB to 0.20 MB.

No blog post would have suggested that fix. The trace pointed straight at it.

That's the argument of this post. **A benchmark is a scoreboard. A profile is a map.** An agent with only a scoreboard is a very fast hill-climber that picks hills by reputation. Give it the map and its hypotheses start coming from your program instead of from its training data.

The examples come from the browser, because that's where we did the work. The second half follows the same questions into CLIs, syscalls, disk, and GPUs. I'll say when a tool is one I'd pick rather than one we actually ran. Docs checked October 5, 2026.

## First, a Scoreboard That Can't Be Fooled

A profiler doesn't replace the benchmark. It needs one: a repeatable workload that shows the problem and proves the work actually got done.

"Make scrolling faster" lets the agent decide what counts as faster. Write the job down instead:

```text
Workload: slow wheel scroll, rapid reversals,
  12 instant top/bottom jumps; pointer over grid.
Measure: p95 frame gap, long tasks, main-thread
  work per phase.
Preserve: selection, keyboard behavior, export,
  shadows and frosted surfaces.
Environment: production build, pinned Chromium,
  1440x1000, 2x CPU slowdown.
Reject: a faster run that skipped the work.
```

The last line looks paranoid until it saves you. Our first scroll baseline used plain Home/End keys and didn't wait long enough for things to settle. The browser's smooth-scroll animation kept running into the next phase, so the "jump" numbers measured a page that was still moving. They looked great.

The harness now asserts every jump endpoint and checks that the document height stays stable. A benchmark that never leaves the top of the page is very fast. It just isn't measuring anything.

The same rule holds outside the browser. A parser benchmark checks that the output didn't change. A load test counts errors as well as latency, because rejecting requests is a remarkably effective way to lower response times.

Keep the baseline's raw runs, commit, tool versions, and hardware. Treat cold and warm caches as separate scenarios. Then hand the agent the command and nothing else yet.

## Wire the Browser for Evidence

We drove Chromium with Playwright and used [CDP sessions](https://playwright.dev/docs/api/class-cdpsession) to get at the browser's instruments. Playwright moves the mouse. CDP records what that cost.

```ts
const cdp = await page.context().newCDPSession(page);
await cdp.send('Performance.enable');
await cdp.send('Emulation.setCPUThrottlingRate', {
  rate: 2,
});
await cdp.send('Network.enable');
await cdp.send('Network.setCacheDisabled', {
  cacheDisabled: true,
});

const network = {
  latency: 150,
  downloadThroughput: 200_000, // bytes/sec
  uploadThroughput: 96_000,
};

await cdp.send(
  'Network.emulateNetworkConditionsByRule',
  {
    offline: false,
    matchedNetworkConditions: [
      { urlPattern: '', ...network },
    ],
  },
);
await cdp.send('Network.overrideNetworkState', {
  offline: false,
  ...network,
});
```

Our original harness used `Network.emulateNetworkConditions`, which is now deprecated. The replacements split request throttling from the network state that page JavaScript sees, and some of them are experimental. Check the [Network domain](https://chromedevtools.github.io/devtools-protocol/tot/Network/) against your pinned browser. If a setting isn't supported, fail setup. Don't quietly benchmark a different environment.

Also label what you actually controlled. [`setCPUThrottlingRate`](https://chromedevtools.github.io/devtools-protocol/tot/Emulation/#method-setCPUThrottlingRate) is a slowdown factor. It doesn't turn a MacBook into a phone, and it doesn't touch the GPU. Disabling the HTTP cache leaves service-worker and other caches alone.

For each phase, the harness collected `requestAnimationFrame` gaps and long tasks from inside the page. It also took before/after snapshots of [`Performance.getMetrics`](https://chromedevtools.github.io/devtools-protocol/tot/Performance/#method-getMetrics) for `ScriptDuration`, `LayoutDuration`, and `RecalcStyleDuration`. Put the units and limits in the report schema, because the agent will round up otherwise:

- Those durations are in seconds, cumulative.
- A frame gap measures when callbacks ran, not what the display showed.
- A heap reading is one moment, not evidence of a leak.
- A Playwright input round trip includes automation overhead. It isn't INP.

So far this is still a scoreboard. It says scrolling got worse. It doesn't say why.

## Read the Map Before Touching the Code

When the counters point at JavaScript, record a CPU profile around the slow phase:

```ts
import { writeFile } from 'node:fs/promises';

await cdp.send('Profiler.enable');
await cdp.send('Profiler.start');

await runScrollPhase(page); // your driver

const { profile } = await cdp.send('Profiler.stop');
await writeFile(
  'scroll.cpuprofile',
  JSON.stringify(profile),
);
```

[`Profiler`](https://chromedevtools.github.io/devtools-protocol/tot/Profiler/) gives you sampled JavaScript stacks. Our problem wasn't JavaScript, though. It was raster and image decode, which happen off the main thread, and only a browser trace shows those. With [`Tracing`](https://chromedevtools.github.io/devtools-protocol/tot/Tracing/), subscribe to events before you start recording, and wait for `tracingComplete` after you stop. Keep the whole trace file. A screenshot of one hot function throws away the evidence that matters.

Our trace summaries counted raster time, image decode time, and raster tasks per scroll. Those three numbers sent us to the animated stickers. Once stills went in, all three fell together: raster tasks dropped from 1,228 to 458 and decode time from 440 ms to 149 ms. A JavaScript profile would have shown an idle main thread and a scroll that still stuttered.

Reading the map takes a little vocabulary, and agents get it wrong in predictable ways:

- **Flame graph vs. flame chart.** In a [flame graph](https://www.brendangregg.com/flamegraphs.html), width is a share of samples and the x-axis is not time. A flame chart keeps time order. Use the chart when you're chasing one stall rather than overall cost.
- **Self time vs. total time.** A wide frame might be doing nothing but calling its children. Make the agent name the frame where the time is actually spent.
- **Stack vs. cause.** A wide `JSON.stringify` stack means something serializes too often or serializes too much. It doesn't mean you need a faster JSON library.

That last one generalizes. The best question a profile raises is not "how do I make this faster?" It's **"why is this happening at all?"** The stills fix didn't speed up raster. It removed raster work nobody needed.

The same question found smaller wins in the grid:

- The pointer crossing cards started animation downloads. A 120 ms hover delay took a 20 ms pass-through from one request to zero, while keyboard focus still played immediately.
- The provider rebuilt its saved-selection lookup on every render. A lazy reducer initializer builds it once.
- A Google Fonts stylesheet blocked the whole selection island while it loaded. We self-hosted the fonts.

Profiling also costs time. Use a short traced run to explain a bad phase, then measure the fix with tracing turned off.

## Same Loop, Different Instruments

Off the browser, the questions stay the same: where does CPU go, what is the process waiting on, and is the accelerator busy or starved? Here's what I'd hand an agent for each. Emoji Brain didn't need most of these.

| Question | Tool | Notes |
| --- | --- | --- |
| Did this CLI get faster? | [hyperfine](https://github.com/sharkdp/hyperfine) | Warmups, repeats, JSON export |
| Where does native CPU go? | [samply](https://github.com/mstange/samply), [perf](https://perfwiki.github.io/main/tutorial/) | samply works on macOS, Linux, and Windows |
| Where does Node CPU go? | [`--cpu-prof`](https://nodejs.org/api/cli.html#--cpu-prof) | Writes a `.cpuprofile`, same format as above |
| Where does Python CPU go? | [py-spy](https://github.com/benfred/py-spy) | Attaches without changing code |
| Is it waiting, not working? | [sysstat](https://github.com/sysstat/sysstat), [strace](https://strace.io/) | Linux; pidstat, iostat, syscall timing |
| Which waits are long? | [BCC](https://github.com/iovisor/bcc) | `offcputime`, `biolatency`; needs privileges |

The scoreboard first. Fixtures must match, and outputs get checked separately:

```bash
hyperfine --warmup 3 --runs 10 \
  --export-json timings.json \
  './baseline-parser fixtures/large.json' \
  './candidate-parser fixtures/large.json'
```

Warmups measure a warm workload on purpose, so they say nothing about cold start. Stateful commands need a reset between runs.

Then the map: `samply record ./parser fixtures/large.json`, or on Linux `perf record -F 99 --call-graph dwarf -- ./parser ...` followed by `perf report`. Profile an optimized build that still has symbols. Under perf, JIT-compiled Node code shows up as anonymous addresses unless you enable [Node's perf integration](https://nodejs.org/en/learn/diagnostics/poor-performance/using-linux-perf).

### When the CPU profile is boring

A request takes four seconds and the flame graph is mostly idle. That isn't a dead end. It means the process is waiting on something, so profile the waiting:

```bash
# Replace 12345 with the workload PID.
pidstat -u -r -d -w -p 12345 1 10
iostat -xz -y 1 10

# Syscall counts, then per-call timing.
strace -f -c -o summary.txt \
  ./parser fixtures/large.json
strace -f -tt -T -e trace=%file,read,futex \
  -o calls.txt ./parser fixtures/large.json
```

Thousands of repeated `openat` calls point at a metadata-heavy build. Long `futex` waits point at lock contention. Neither one is a CPU problem, so rewriting a loop won't touch it. If averages look fine but the tail is ugly, BCC's `offcputime` shows the stacks that were waiting, not running. strace slows syscall-heavy programs a lot, so use it to diagnose and rerun the timings without it.

One warning the agent needs in writing: perf, strace, and BCC don't become macOS tools because the agent typed their names confidently. On a Mac, use samply or Instruments, and run the Linux tools on the Linux host where the workload actually runs. If a profiler is blocked by permissions, the agent should report that and stop. It shouldn't loosen host-wide settings to get around it.

## Ask Which GPU You're Measuring

Our default headless Chromium rendered with SwiftShader, which is software. The windowed run used Metal on an Apple M2. Same build, same benchmark, different rendering paths. The `will-change` regression was measured on SwiftShader, and a result on one path tells you nothing about the other.

Record what the browser actually got:

```ts
const browser = page.context().browser()!;
const session =
  await browser.newBrowserCDPSession();
const { gpu } = await session.send(
  'SystemInfo.getInfo',
);
await session.detach();

report.renderer = {
  devices: gpu.devices,
  features: gpu.featureStatus,
};
```

[`SystemInfo`](https://chromedevtools.github.io/devtools-protocol/tot/SystemInfo/) tells you which renderer you got. It doesn't measure throughput. Even the browser channel doesn't guarantee a GPU, so check the recorded status on every run.

For GPU compute, work from coarse to fine:

1. [`nvidia-smi`](https://docs.nvidia.com/deploy/nvidia-smi/index.html): busy, memory-bound, or power-limited? It's coarse. A one-second sample misses short stalls, and high utilization doesn't mean efficient work.
2. [Nsight Systems (`nsys`)](https://docs.nvidia.com/nsight-systems/UserGuide/index.html): the CPU/GPU timeline, with launches, copies, syncs, and the gaps between kernels.
3. [Nsight Compute (`ncu`)](https://docs.nvidia.com/nsight-compute/NsightComputeCli/index.html): why one particular kernel is expensive.

```bash
nsys profile --trace=cuda,nvtx \
  --sample=none --cpuctxsw=none \
  -o workload ./cuda-app
nsys stats workload.nsys-rep
```

Start with the timeline. If the GPU sits idle because the CPU can't feed it, tuning kernels is premature, the same way rewriting a loop is premature when the process is blocked on a lock. `ncu` replays kernels to collect counters, so treat its runs as diagnostics, not timings. On Apple hardware, use [Metal System Trace](https://developer.apple.com/metal/tools/). On AMD, use [ROCm's profilers](https://rocm.docs.amd.com/projects/rocprofiler-sdk/en/latest/). GPU profiling is not a synonym for CUDA.

## Make Every Change Earn Its Place

Here is the containment experiment from the opening, as the agent should report it. Three-run medians, 1440 × 1000, 2× CPU slowdown:

| Interaction | Baseline p95 gap | Containment p95 |
| --- | ---: | ---: |
| Slow wheel | 16.8 ms | 33.3 ms |
| Rapid reversals | 16.8 ms | 50.0 ms |
| Instant jumps | 16.8 ms | 16.8 ms |

Main-thread work for jumps fell from 437 to 319 ms. Rapid reversals rose from 824 to 1,335 ms. Containment helped one motion and hurt two, so [we rejected it](https://github.com/justsml/emoji-brain/blob/5f6c209/docs/performance/selection-scrolling.md). A benchmark that only jumped would have shipped it.

An environment flag (`SCROLL_CONTAINMENT_EXPERIMENT=1`) made the experiment cheap to repeat. Both arms ran the same build with one switch flipped. A feature flag or two binaries work just as well elsewhere. What matters is that any difference can only come from the change.

Each experiment needs a hypothesis written before the edit, along with the number it expects to move. "Hover intent will stop incidental animation requests without delaying focus playback" can be checked. "This should be faster" can't.

Some of the cost is the product. We kept the grid's shadows and frosted surfaces. Dropping `backdrop-filter` measured only about 8% better, and we said no. Put that kind of decision in the instructions, or "faster" quietly turns into permission to delete the design.

Once a candidate looks good, alternate baseline and candidate runs to cut time-of-day bias. Report the spread, not just a median. Ten whole-command timings do not make a p99. Keep the failed experiments too, labeled. The rejected containment run is in the repo, and it's the most useful file there.

## The Instructions I'd Give the Agent

Once the harness and instruments exist, the prompt is boring. That's the goal.

```text
Reproduce the workload with the documented
  benchmark. Record baseline, environment, and
  correctness before editing.

Profile or trace the slow phase. Name the dominant
  cost and ask why that work happens at all.

Write the hypothesis and expected metric change.
  Change one thing. Preserve output, behavior,
  and design constraints.

Rerun every workload with tracing off. Keep raw
  reports and profiler artifacts.

Reject regressions in any phase. Never relax a
  threshold to pass. If the instrument or
  environment is invalid, fix that first.

Report what improved, what regressed, and what
  is still unmeasured.
```

Keep a ledger next to the artifacts: commit, workload, hypothesis, settings, commands, result, decision. Feed the agent JSON or CSV, and keep the original traces for a human to open. When you need the same summary from a dozen recordings, [Perfetto's trace processor](https://perfetto.dev/docs/analysis/trace-processor) lets you query traces with SQL.

The agent brings speed. It reads unfamiliar code quickly, wires up experiments you'd skip, and tries ideas you wouldn't bother with. You bring the definition of useful work and the rules for when a result counts. The profiler covers the part neither of you can supply from memory: where this particular program spends its time.

Without one, the agent tuned our grid with the two tricks from the blog posts. Both made it worse. With a trace, it found 92 dancing stickers repainting every frame, and cut raster time by more than half.

Give it a profiler.
